# A Theory of Metadator

## What the system is for

Metadator exists because Obsidian notes accumulate without metadata. A vault of two thousand notes becomes navigable only if each note carries tags, a description, and optionally a title in its YAML frontmatter — but writing that metadata by hand, note by note, is drudgery that people don't do. The plugin automates it: the user opens a note, runs a command, and the plugin reads the note's content, asks Claude to characterize it, and writes the result into the frontmatter.

The problem domain has three entities. A **note** is a markdown file with optional YAML frontmatter fields. **Metadata** is the set of structured properties written to that frontmatter — currently tags (an array of lowercase hyphenated terms), a description (a sentence or two), and an optional title (a short phrase). A **generation** is a single round trip: extract content from the note, send it to Claude, parse the response, and write results. The plugin mediates between the note (an Obsidian file) and the LLM (the Anthropic API), translating between the freeform world of prose and the structured world of frontmatter.

## The organizing ideas

**One command, one note, one API call.** The plugin does not batch. There is no queue, no background processing, no vault-wide sweep. The user triggers generation manually for the note they are looking at. This is a deliberate constraint, not a missing feature — it keeps the plugin stateless between invocations and avoids the complexity of progress tracking, cancellation, and partial failure across many files. Every run is independent.

**The update method is the central policy decision.** The system has exactly two modes: `preserve_existing` (only populate empty fields) and `always_regenerate` (overwrite everything). This binary controls whether the plugin is additive or authoritative. The names are the result of a deliberate renaming from earlier terms (`force`, `update_all`, `no-llm`, `empty_only`) that were ambiguous about intent — the migration code in `main.ts` is the fossil record. The current vocabulary is load-bearing: code throughout `metadata.ts` branches on whether `force` is true, where "force" means `always_regenerate`. This is the one setting that determines whether running the command on an already-tagged note is safe or destructive.

**Tags are special.** Among the three metadata fields, tags are the only one that uses `append` semantics rather than `update`. When `always_regenerate` is active, description and title are overwritten, but tags are merged with deduplication. This reflects the domain reality that tags accumulate — a note about "machine learning" that also touches "ethics" shouldn't lose its first set of tags when re-analyzed. The `updateFrontMatter` function handles this: `append` mode concatenates arrays and deduplicates via `Set`; `update` mode replaces wholesale; `keep` mode writes only if the field is `undefined`. This three-way write method is the most nuanced abstraction in the codebase, and it exists because tags needed it.

**The prompt is constructed, not stored.** There is no prompt template file. `buildPrompt` assembles the system message from the user's per-field prompt strings (configurable in settings) and a JSON schema example. When `enableTitle` is false, the title instruction and its JSON field are simply omitted from the system message. The user message wraps the note content in `<article>` XML tags. This construction is straightforward but it means the prompt's structure is coupled to the settings interface — adding a fourth metadata field would require changes in `buildPrompt`, `generateMetadata`, `addMetadataWithClaude`, and the settings type. The system is shaped for three fields, not N.

**Response parsing is defensive by design.** `parseMetadataResponse` uses a layered strategy: first, find all non-greedy `{...}` matches and try parsing each as JSON, preferring the last valid one (because LLMs tend to put the answer last, after preamble). If that fails, try extracting from code fences. If that fails, try a greedy `{...}` match for nested braces. Each candidate is validated with `isValidMetadataResponse`, which checks that all present fields are strings. This parser replaced an earlier greedy regex that broke when Claude's response contained multiple JSON-like objects — the changelog and tests document this explicitly. The parser is also where the system absorbs the most unpredictability from the outside world: Claude's output format is a suggestion, not a guarantee.

**Frontmatter writes go through Obsidian's API, always.** `updateFrontMatter` delegates to `app.fileManager.processFrontMatter()`, which is Obsidian's sanctioned way to modify YAML frontmatter. The plugin never parses or serializes YAML itself. This is a principled boundary: Obsidian owns the file format, and the plugin trusts it to handle edge cases (multiline strings, special characters, ordering). The consequence is that each field write is a separate async call to `processFrontMatter`, which means three sequential file operations per generation. This is correct but not optimizable without Obsidian changing its API.

**Content truncation is a cost-management feature, not a quality feature.** The plugin tokenizes note content with a regex that handles CJK characters (one token per character), Latin words, punctuation, and newlines. Three truncation strategies exist: `head_only` (first N tokens), `head_tail` (80/20 split of beginning and end), and `heading` (outline extraction with first-paragraph summaries). The tokenizer is approximate — it doesn't match any real LLM tokenizer — but it doesn't need to. Its purpose is to keep API costs bounded for long notes, not to predict exact token counts. The default limit is 1000 tokens, which is conservative.

## The seams

**The Anthropic SDK boundary.** `callClaude` in `utils.ts` is the only function that touches the network. It instantiates a new `Anthropic` client per call (no reuse), sets `dangerouslyAllowBrowser: true` because Obsidian's Electron renderer is a browser context, and hardcodes `max_tokens: 2048`. Error handling maps SDK exception types to user-facing `Notice` messages. The function both displays UI (the "Generating metadata..." notice) and performs the API call — it is not purely a network layer but also a UX layer. This coupling is pragmatic for a plugin this size but means you cannot call Claude without showing a notice.

**The Obsidian API boundary.** The plugin uses four Obsidian APIs: `app.workspace.getActiveFile()` (to get the current note), `app.metadataCache.getFileCache()` (to read existing frontmatter without parsing YAML), `app.vault.read()` (to get raw content), and `app.fileManager.processFrontMatter()` (to write frontmatter). These are accessed through the `App` object threaded through function parameters. The test-preload file (`test-preload.ts`) mocks these with minimal stubs — `Plugin`, `Notice`, `PluginSettingTab`, and `Setting` are all replaced with empty classes. The tests never test against real Obsidian; they test the logic between the seams.

**Settings migration.** `migrateSettings` in `main.ts` runs on every load. It rewrites legacy values for `updateMethod` (four old names to two current ones), `anthropicModel` (date-stamped model IDs to short aliases), and `maxTokens` (renamed to `contentTokenLimit`). This function is the only place where backward compatibility lives. It is idempotent and accumulates — each new rename adds another `if` clause. The tests cover every known migration path. If you add a new setting name, you add a migration clause here and a test for it.

**The JSON parse boundary.** Between Claude's response string and the typed `MetadataResponse`, the parser must tolerate whatever Claude returns. The tests document specific adversarial cases: prose with braces before valid JSON, multiple JSON objects, code fences with and without language specifiers, values containing backticks. This is the thinnest part of the theory — the parser works for observed cases but there is no formal grammar. A response containing valid JSON with unexpected field types (numbers, arrays, nulls) is explicitly rejected by `isValidMetadataResponse`, which is good.

## What the system accommodates easily and what it resists

**Easy changes:** Adding a new Claude model is trivial — add a dropdown option in `settingsTab.ts` and optionally a migration in `main.ts`. Changing the default prompts is a one-line edit in `settings.ts`. Changing field names (the frontmatter keys) is already user-configurable. Adjusting truncation parameters requires no structural changes. Adding a new truncation method requires one new function in `utils.ts` and a clause in `getContent`.

**Moderate changes:** Adding a fourth metadata field (say, `category`) would require touching `settings.ts` (new fields), `settingsTab.ts` (new UI section), `buildPrompt` (new instruction), `addMetadataWithClaude` (new write block), `MetadataResponse` (new optional field), and the integration tests. The pattern is clear from the existing three fields, but there is no abstraction that makes this automatic — you are copy-pasting and adapting the description/title pattern each time. The system is shaped for a small, fixed number of fields.

**Hard changes:** Batch processing (running on many notes) would require rethinking the entire flow, which assumes one active file, synchronous user attention, and `Notice` for feedback. Making the plugin reactive (auto-generating metadata on file save or creation) would require a different lifecycle hook and careful debouncing. Switching from Anthropic to another LLM provider would require replacing `callClaude` and potentially the prompt format, but nothing else — the boundary is clean. Supporting non-string metadata types (dates, booleans, nested objects) would require rethinking `MetadataResponse`, the parser, and `updateFrontMatter`.

## Uncertainties and tensions

**The duplicate commit history.** The git log contains pairs of commits with identical messages but different hashes (e.g., `49d7ca1` and `2df7a6a` both say "chore: rebuild main.js for distribution"). This looks like a rebase or cherry-pick that replayed a branch onto main, creating parallel commit sequences. It is cosmetic — the code is consistent — but it means `git bisect` may land on either copy.

**The `truncateHeading` body offset problem.** The walkthrough document flags this and I concur: when the outline fits within the token budget and body text is appended, the body is sliced from `tokens[totalTokens.length]`, where `totalTokens` is the count of tokens in the _reconstructed outline_, not the original document. The outline rearranges content (keeping headings, truncating paragraphs), so the positional index into the original token array doesn't correspond to "content not already in the outline." In practice this means the body section may skip or repeat content. The test `body does not duplicate outline content` was added to address a related bug, but it only checks that the body doesn't start with `#` — it doesn't verify positional correctness. This is the area most likely to produce wrong output for notes with many headings.

**The Zod experiment.** Commit `864cad4` added JSON schema validation with Zod; commit `2f6d1ee` reverted it. The current `isValidMetadataResponse` is a hand-rolled type guard. I infer the revert was motivated by bundle size or dependency concerns for an Obsidian plugin, but this is speculation — there is no ADR or commit message explaining why. The hand-rolled validator works but is more fragile to extend.

**The `writeField` truthiness problem.** `writeField` returns `method !== "keep"` regardless of whether the write changed anything. When `append` deduplicates tags and all new tags already exist, `hasChanges` is still `true` and the user sees "Metadata updated successfully" for a no-op. This is noted in the walkthrough and remains unfixed. It is a UX imprecision, not a data integrity issue.

**`updateFrontMatter`'s silent ignore.** If `method` is `append` but `value` is a string, the function does nothing — no error, no write. The caller always passes arrays for tags and strings for description/title, so this path is never triggered. But the function's contract is implicit; a future caller could hit this silently. Whether this is a latent bug or acceptable narrowness depends on whether `updateFrontMatter` is meant to be a general utility or a private helper. Its export suggests the former; its behavior suggests the latter.

**`isDesktopOnly` oscillation.** The manifest field `isDesktopOnly` was set to `true` in commit `16b75bd`, reverted to `false` in `457dde9`, and reverted again to `false` in `6219608`. The current value is `false`, meaning the plugin claims mobile compatibility. Whether it actually works on Obsidian Mobile — where the Anthropic SDK's `dangerouslyAllowBrowser: true` runs in a genuine mobile webview rather than Electron — is an open question. The repeated flipping suggests uncertainty about this.

**No `styles.css`.** The walkthrough flags this as a community plugin submission requirement. The release workflow attaches `main.js` and `manifest.json` but no `styles.css`. If the plugin is submitted to Obsidian's community directory, this will need addressing. If it remains a private plugin installed via manual copy (the `deploy` script copies to a local vault), it doesn't matter.

**The prompt always asks for all fields.** When `preserve_existing` is active and two of three fields are already populated, the plugin still asks Claude to generate all three and discards two of the results. This wastes tokens and money but simplifies the code — the prompt doesn't need to be conditional on which fields are missing. Whether to optimize this depends on how often the plugin is run on partially-tagged notes versus fresh ones.
